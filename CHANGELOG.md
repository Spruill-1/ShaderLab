# Changelog

All notable changes to ShaderLab will be documented in this file.
Format follows [Keep a Changelog](https://keepachangelog.com/).

## [1.9.0] - 2026-09-18

### Changed

- **Gamut option labels are consistent.** Id 1 reads **Display P3** everywhere, and Gamut Highlight and Gamut Source say sRGB / BT.2020 instead of Rec.709 / Rec.2020, matching the other effects (the primaries and white are the same). Effect versions: Gamut Highlight 6, Gamut Source 5, Gamut Coverage 9, Gamut Map 8, ICtCp Gamut Map 14, ICtCp Boundary 6, ICtCp Gamut Boundary LUT 4, Gamut Parameter 3.
- **An unwired lookup input of a D3D11 compute node gets the 1x1 zero placeholder**, as a pixel shader's already did. The compute path used to pass the bridge a null texture, which failed the dispatch, so a compute effect could not have an optional table.
- **Performance pass: every Tier 1 item from the 2026-09-25 review except output-window resolution (kept by design).** All figures are measured on this machine (Snapdragon / Adreno, ARM64 Release), headless `gpu-bench` with D3D11 timestamps unless stated; "min" is the fastest of 15-40 iterations. The instrument was validated first (analysis values moved with the input, no `[ShaderLab]` stderr faults), and every changed output was compared against a pre-change FP32 capture of the same regions.
  - **End to end.** A 2880x1800 HDR capture feeding Luminance Statistics, ICtCp Tone Map (GPU-bound to the stats), a pixel-shader tone mapper, Delta E and a second Luminance Statistics: GPU frame **34.6 -> 14.1 ms** (min; median 40.7 -> 14.1 on a quiet machine) and CPU time to evaluate **37.5 -> 0.4 ms** in the GUI's configuration. Every analysis value is unchanged except Mean/AvgLog, which move by at most 4e-5 relative (float summation order, below).
  - **No more Evaluate-time pre-render** (#0, #18). `Evaluate` rendered each image-compute input into a *new* full-size FP32 bitmap (133 MB at 4K) per dirty frame -- a snapshot `ProcessDeferredCompute` then threw away whenever the producer was dispatched in the same pass. The in-session render there is the fresh one by construction, so it is now the only one, into persistent targets keyed by producing node and pin (#6: the old image-pointer key leaked one FP32 surface per recreated upstream effect). An input that is already an FP32 bitmap covering its bounds -- another compute node's output -- is bound directly with no copy, and inputs are resolved from the graph at dispatch time rather than trusted from the queue. `PreRenderInputBitmap` is deleted, which also removes a nested-`BeginDraw` hazard. Decision #95.
  - **Compute shaders are no longer recreated every frame** (#1, #10, #17, #54, #89). A GPU-bound consumer swapped variant bytecode in and the baseline back after every dispatch, so each frame paid two `CreateComputeShader` calls plus canonicalising and hashing ~30 KB of HLSL and a `D3DReflect`. Bytecode is now identified by the compiler's 16-byte DXBC checksum: the bridge treats a same-checksum `SetCompiledBytecode` as a no-op and keeps a few created shaders, and the evaluator memoizes variants and reflection by checksum. `IncludeLibraryHash` is computed once. Decision #96.
  - **Asynchronous analysis readback in the GUI** (#37). Each CPU readback `Map`ped straight after its dispatch, draining the whole GPU pipeline once per compute node, in series. The runner now has a 3-slot staging ring; in the GUI's live loop a needed readback is queued and collected on a later frame (`DO_NOT_WAIT`), re-dirtying whatever is bound to the values when they land. Headless, tests and MCP-forced frames still read blocking. Decision #97.
  - **Statistics reductions use the whole GPU** (#52). Luminance / Channel / Chromaticity Statistics, CIE Histogram and Gamut Coverage each ran as *one* 32x32 thread group walking the frame on a single CU. A shader can now opt into `SHADERLAB_REDUCE_SCRATCH` (in `shaderlab_params.hlsli`): the host dispatches 64 groups with a scratch buffer, each group writes its partial, and the last group to finish (atomic counter) folds them. Min/Max/percentiles/counts are exact; Mean and AvgLog differ by <= 4e-5 relative because each thread now sums ~80 values rather than ~8,100 -- if anything closer to the true value. Saved graphs keep their single-group HLSL until upgraded. Decision #98.
  - **ICtCp Gamut Map Fit to Shell: 1,924 ms -> 2.0 ms per frame** at 1 Mpx (x940); modes 0/1/3 2.3-2.9 -> 2.1-2.2 ms; **ICtCp Boundary 6.1 -> 2.8 ms** (#50, #51). Both rebuilt gamut-boundary polygons -- functions of the parameters alone -- for every pixel. A new descriptor hook, `deriveConstants`, lets a built-in compute such tables on the CPU once per parameter change (memoized) and upload them as cbuffer arrays; `Effects/ColorMathCpu.h` is the CPU port of the ICtCp path it needs, pinned to the HLSL by a GPU cross-check test (agreement 1.2e-5). Gamut Map reads a 256-entry fit-scale table (mode 2) and a 64-level target polygon (modes 0/1/3), interpolated in I: **max 0.11 dE ITP** from the exact per-pixel result on a saturated BT.2020 gradient, mean <= 0.012. Decision #99.
  - **Scale: 10-48x faster downscales** (#56): Lanczos-3 2x 17.6 -> 1.7 ms, 4x **94.6 -> 1.9 ms**, Catmull-Rom 3x 46.9 -> 1.1 ms; a 1.5x Gaussian upscale is unchanged (5.5 ms). The 2-D kernel is separable, so each 8x8 tile filters the source rows it needs horizontally into groupshared and then vertically, streaming rows through a 2 KB buffer (an 8 KB one halved upscale speed from occupancy alone). Output differs from the old 2-D loop by <= 7e-6 (summation order).
  - **Hardware-decoded video stays on the GPU** (#70): the decoder surface is copied GPU-side into a planar NV12/P010 texture read through plane views, instead of a `Lock2D` readback, memcpy and re-upload. 4K HEVC Main10 decode+upload **10.2 -> 1.4-1.7 ms per frame**; the output is byte-identical to the CPU path (tested on WARP and hardware).
  - **Edits dirty only what changed** (#87, #111, #127). Every property edit, slider drag, MCP `set-property`/`connect`/`add-node`/`remove-node`/`compile`/`apply`, preview switch and capture called `MarkAllDirty`, so each was a worst-case full-graph frame. The evaluator already pulls dirtiness downstream along edges and bindings; the one reason callers could not rely on it was that it *discarded* a pending change on a node not currently needed. It now keeps it (and `HasDirtyNodes` ignores unneeded nodes), `RemoveNode` dirties the removed node's consumers, and ~40 call sites dirty the edited node only. Load, clear, device/adapter change, display-profile change and forced redraw still dirty everything. Decision #100.
  - **Smaller items in the same set:** a node whose compile or effect creation fails no longer stays dirty forever, which had cost every frame a second Evaluate plus the frozen pass (#23); the D2D Histogram is read only when dirty and never inside the draw session (#19); a binding consumer of a compute node is queued once per cycle -- the second Evaluate pass used to queue it again, dispatching it twice, and headless now takes that pass only when needed, like the GUI (#128); desktop duplication ignores pointer-only updates, which copied the desktop and re-evaluated the graph on every mouse move (#72); cached sources whose node is gone are dropped, so a deleted capture stops copying frames and forcing renders and a deleted video stops decoding (#68); a paused or static video no longer re-seeks and re-decodes every tick (#69, #77, below); output windows present only when a new frame or view change exists and stop rebuilding XAML each tick, and their cost now appears in the perf readout (#106).
  - Engine ABI bumped to 5. The video test's clips are generated, not checked in: `Tests/fixtures/MakeVideoFixtures.ps1` (ffmpeg) writes a single-keyframe 4K HEVC Main10 clip and a 320x180 H.264 High clip, and the test reports `[SKIP]` without them, so CI (no ffmpeg) is unaffected. On the 4K clip zero-copy measured 1.8 vs 16.8 ms per frame. `Tests/TestRunner.cpp` gains regression tests for each behaviour above; tests confirmed to fail with a fix disabled where practical (the dispatch-once test reads 3 dispatches without it).

- **The shared color math is an include, `shaderlab_colormath.hlsli`, and both engine headers are optional** (decision #109, [docs](docs/effects/effect-designer.md#engine-headers)). Built-in shaders no longer have `GetColorMathHLSL()` prepended at registration; each one that uses the library says `#include "shaderlab_colormath.hlsli"` next to its `#include "shaderlab_params.hlsli"`, and the video export converter and the shader test bench do the same. One include handler, `ShaderLabIncludeHandler()`, serves both names to every compile path (evaluator, bytecode cache, graph and user-effect loading, Effect Designer, MCP `effect_compile`, `D3D11ComputeRunner`, video export, tests). The library now has an include guard, and `IncludeLibraryHash()` covers its text, so editing `ColorMath.cpp` invalidates cached bytecode. The Effect Designer scaffold (and the editor templates) include both headers; an author may delete either and paste code in instead, which pins that shader to the math it was written against. No `effectVersion` moved: the change is bytecode-neutral. Compiling each built-in's old prepended source and its new include form with the same flags and macros gave byte-identical DXBC for all 22 that compile (both binding modes of the five GPU-bindable ones), and for the video export shader; `Gamut Coverage` failed to compile in both forms (32,772 bytes of groupshared against the 32,768 limit, independent of this change; fixed below). Saved graphs are not migrated: one that embeds the old prepended text is self-contained and compiles as before. `ColorMathHlsli_*`, `NoIncludes_*`, `InlineLibrary_*` and `IncludeLibraryHash_*` tests cover the include, its equivalence to the prepended form for every built-in, shaders with neither include, and the cache key.
  - **A third optional header, `shaderlab_gamut.hlsli`** (decision #110, [docs](docs/effects/effect-designer.md#engine-headers)), holds the exact gamut boundary search (`InTargetCube`, `InTargetCubeRgb`, `CubeBoundaryRadius`) and the `ICtCp Gamut Boundary LUT` contract: table size (`GAMUT_LUT_W/H`, set from the C++ constants the generator allocates with), row warp, the column/row reader (`GamutLutColumnFor`, `GamutLutRadiusAt`, `GamutLutBoundaryRadius`) and the stamp (`GamutLutStampAlpha`, `GamutLutStampMatches`). It includes the color math itself and has an include guard. The LUT generator, which had `GamutBoundaryHLSL()` prepended, now includes it, and so does the out-of-tree screenshot tone mapper, which carried a hand copy of the same helpers; the producer and its readers now compile one text. Byte-identical DXBC before and after for the generator and for the tone mapper in its generic, GPU-bound and two specialised builds, so no `effectVersion` moved. The same handler serves it and `IncludeLibraryHash()` covers it. The Effect Designer scaffold does not include it. `GamutHlsli_*` tests cover it alone, after and around the color math, twice, its equivalence to the pasted form for the generator, and the cache key.
- Knee solved from a perceptual white-error budget, and several further iterations of the since-removed HDR screenshot tone-mapping effect (decision #101; its history is kept out of tree).
- **The gamut-boundary early-out in `ICtCp Gamut Map` now fires.** It guarded a 48-point boundary walk (a ray intersection per segment, per pixel) behind `if (r > 1e-6)`, intended to skip achromatic pixels — but a neutral's residual chroma after the scRGB → ICtCp round trip is 3.4e-6 to 2.9e-5, *above* that threshold, so the early-out never triggered and every neutral pixel paid the full walk. Raised to `1e-3`, which is still only ~1% of the O(0.1) boundary radius, so nothing meaningfully compressible is skipped. **Verified bit-exact**: 24/24 probes identical across neutral, near-neutral, in-gamut saturated and wide-gamut (negative-component BT.2020) colours through the effect. **Measured 1.40× faster on achromatic content** — but only after the measurement itself was fixed twice. The first harness timed nothing: `{"op":"render"}` builds the D2D effect graph without rasterising it, and `pixel-region` evaluates only the region it asks for, so a "4K render" followed by a 1×1 readback shaded exactly one pixel. `capture-node` is the only op that forces a full-frame draw. The second problem was drift: absolute timings moved 2.5× between sessions *on the saturated case, which the change cannot affect*, so cross-session comparison is worthless here. Interleaving achromatic and saturated within each rep and using the saturated frame as an internal control gives the robust statistic — the achro/sat ratio goes **0.823 → 0.588** across the threshold change, so the walk is `0.823 − 0.588 = 23.5%` of a saturated frame and an achromatic frame gets 1.40× faster. A normalised cross-session estimate lands on 1.40× independently. Note this **contradicts the figure this change was proposed from**: the walk is ~24% of frame cost, not 91.3%, and the win is 1.4×, not ~2×. Debug build, 2048×2048, 7 interleaved reps. Per-effect GPU timestamp queries in `Effects/Performance.h` would still be worth having; wall-clock needed three attempts to produce one trustworthy number.
- **A single non-finite texel no longer turns the ICtCp suite's output into roughly −10000 nits.** `ICtCpToScRGB` clamps its PQ-encoded LMS to `[-1, 1]` to keep `PQ_EOTF`'s rational form off its pole — but `clamp()` with a NaN operand is not required to pick either bound, and the observed result was `-1`, which `PQ_EOTF_Signed` then expands to −10000 nits (scRGB −125). One bad texel from a third-party HDR swapchain therefore poisoned every downstream mean, max and dE with a large, *confidently signed* value rather than an obviously broken one. Reproduced end to end by injecting quiet-NaN / ±Inf bit patterns through a `Custom Pixel Shader` node via `/effect/compile`: `ICtCp Tone Map` returned `(-124.92, -125.05, -125.02)`. Non-finite components are now mapped to 0 before the clamp, so a bad texel degrades to black — same probe now returns `(0, 0, 0)`. Deliberately guards **only the inverse**: `ScRGBToICtCp` is left alone so `ICtCp Round-Trip Validator`, the suite's one free correctness oracle, still surfaces a non-finite input instead of being taught to hide it. The test is a **bit test on the exponent field, not `isfinite()`** — these shaders compile with `D3DCOMPILE_OPTIMIZATION_LEVEL3` and no `D3DCOMPILE_IEEE_STRICTNESS`, so the compiler is entitled to assume finite operands and fold `isfinite()` (or any magnitude comparison against a NaN, which is unordered) to a constant. Three regression tests, confirmed to fail with the guard removed — note that "returns finite values" alone does **not** catch it, because −125 *is* finite; the magnitude assertion is the one that bites.
- **`/render/pixel-region` returned HTTP 200 with a body that was not valid JSON.** `"%.6f"` emits the bare C tokens `nan` / `inf` / `-inf`, which have no JSON literal, so a readback over non-finite pixels produced `"pixels":[nan,inf,-inf,1.000000]`. The headless script runner did not fail — it silently embedded the unparseable body as a **string**, so a caller saw a successful-looking read and got no data. That is precisely the shape of failure that yields a complete, plausible, wrong table. Non-finite components now emit JSON `null`. The same loop also appended `snprintf`'s return value, which is the length it *would* have written rather than what it did — a truncated write therefore read past the 32-byte buffer; the buffer is now 64 bytes and the count is clamped.
- **Non-finite values are now JSON-legal everywhere, not just in `pixel-region`.** The earlier fix covered one of roughly seven float-into-JSON sites; `/analysis`, `/graph/node` and the GUI's `/render/pixel-trace` still emitted bare `nan` / `inf` at HTTP 200, and a non-finite value that reached a bound property serialised into a saved document as `1.#QNAN` -- an `.effectgraph` no JSON parser will load, on the binding recipe this release newly recommends. A single `JsonFloat` helper now backs every site, and the property-binding write-back refuses non-finite values outright (recording it in `runtimeError`) so one cannot reach a document in the first place.
- **`/graph/set-property` still accepts any key — a guard was written, measured against the suite, and reverted.** The hole is real: a typo, or a parameter removed by an `effectVersion` bump, returns 200 and lands in the properties map, where it serialises into the saved document and does nothing — a caller mistake turned into a no-op on the exact path this project uses to drive measurements. But validating the key against `customEffect->parameters` rejects a whole class of **valid** calls, because several legitimate keys are absent from both that list and `node->properties` until first written: every un-seeded D2D built-in property (`Gaussian Blur`'s `Optimization` and `BorderMode`), `Clock`'s `IsPlaying` mirror, `shaderPath`, and numeric index keys. `Tests/RunTests.ps1` `Graph.SetProperty` asserts one of them, and it failed. The guard also had a one-call bypass — `/graph/apply` writes property maps unchecked — so it would have cost working calls to close a hole that stayed open next door. Reverted, with the finding recorded at the call site: closing it properly means resolving a key the way `GraphEvaluator::ApplyProperties` does, built-in `GetPropertyIndex` included, and guarding `/graph/apply` on the same predicate. Recorded here because the attempt is the useful part — rejecting valid input is worse than accepting invalid input on a route whose callers are scripts.
- **The Effect Designer and `/context` were still teaching the retracted TEXCOORD rule** -- the generator emitted a two-parameter signature with `Load(int3(uv0.xy, 0))` and a shared `TEXCOORD0` for every input, i.e. it structurally reproduced the defect `Split Comparison` was just fixed out of, for every new user effect; and `GET /context` served the same rule to every connecting MCP agent. Both now emit and describe the correct contract, with one TEXCOORD per input. `.context/resume.md` and `docs/architecture/d2d-d3d11-hybrid-compute.md` corrected likewise; the latter also gained the split draw-session contract and the downstream-freshness rule.
- **`RunRender` never pumped Working Space.** The `--output` / `--pixels` path constructed no `DisplayMonitor` at all, so a saved graph containing a Working Space node rendered against the 80-nit `hiddenDefaults` -- which is precisely the golden-image path the earlier entry told readers to re-take baselines for. Fixed; `RunScript` already had it.
- **Added `TestPixelShaderSignatures`, the structural guard that would have caught all three shader defects.** Nothing in the suite could see a coordinate-semantics problem: the catalog test checks counts and ids, and the render tests assert only `HasOutput() && runtimeError.empty()`, which a blank diagram and an all-black identity both satisfy -- 306/306 passed with a blank `ICtCp Boundary` and two displaced shaders in the same DLL. The new test scans every pixel-shader descriptor's HLSL: a shader taking TEXCOORD must declare `SCENE_POSITION`, none may declare it twice, and a multi-input shader must take one TEXCOORD per input. No GPU needed. Verified to fail (naming the shader) when a duplicate semantic is reintroduced.
- **Transposed P3 constants in the wide-gamut metric.** `Measure-WideGamut`'s "P3 red" landed at CIE x=0.816 y=0.192 -- outside the spectral locus -- and "P3 green" at 0.295/0.617, which is Rec.709 green. They were matrix rows with elements borrowed across rows. Corrected values round-trip to 0.680/0.320 and 0.265/0.690 exactly. The BT.2020 constants in the same table were checked and are correct.
- **Stale comments swept**, including several this work created: the residue-clamp comment still claimed "~1.07x overshoot, a few percent" when the asymptote at the shipped `GamutThreshold` of 0.99 is 1.000075 (0.0075%, computed across thresholds); `renderFrame is a no-op` sat directly above a call that is a full evaluation in headless; a region cap documented as 32x32 was enforced at 64-per-axis/1024-area; an `HRESULT beginHr` held `EndDraw`'s result; and several sites pointed at `MainWindow::OnRenderTick` for structure that lives in `RenderFrameToOffscreen` (the draw-session sequence) or `RenderWorkerLoop` (the Working Space pump) -- the thread is what makes the graph-access rule apply, so the misdirection mattered.
- **Twelve effects had their `effectVersion` bumped, without which none of the shader fixes would have reached an existing document.** A saved `.effectgraph` stores its own `hlslSource` and is recompiled from that stored string on load, so a corrected shader in the registry never reaches a saved graph on its own -- the only upgrade affordance is gated on `desc->effectVersion > node->...->shaderLabEffectVersion`. The first pass bumped exactly one effect and left eleven changed shaders un-bumped, so the headline displacement fix would have shipped to new graphs only. Bumped: Gamut Highlight 4->5, Nit Map 1->2, Split Comparison 7->8, ICtCp Gamut Map 11->12, ICtCp Round-Trip Validator 3->4, ICtCp Saturation 2->3, and the six source generators whose semantic was relabelled (CIE Chromaticity Plot 5->6, Gamut Source 3->4, Color Checker 1->2, Zone Plate 1->2, Gradient Generator 2->3, HDR Test Pattern 1->2). The last six are behaviourally inert -- measured bit-identical -- but `ShaderLabEffects.h` says to increment on any HLSL change, and selectively ignoring that convention is how this drift started. **Existing graphs need "Update All Effects" to pick the fixes up.**
- **A regression introduced and removed within this work, recorded because the mechanism is instructive:** the source-generator relabelling sweep selected on "reads no input" rather than "lacks SCENE_POSITION", so it also rewrote `ICtCp Boundary` -- which already had the correct three-parameter signature -- producing a **duplicate `SCENE_POSITION`** that fxc accepts silently. Its `uv0` is a normalized consumer (`(uv0.xy - 0.5)`), so with pixel coordinates arriving instead the diagram collapsed to a flat field. Caught by adversarial review, reverted; the effect now measures 10 distinct colours across a scanline where a blank field reads 1-3. `CLAUDE.md` names ICtCp Boundary as one of four sanctioned ways to LOOK at wide-gamut content, so it would have silently blanked a tool the project's own instructions point at.
- **Every input-sampling pixel shader mis-read its input, and it was invisible at the default source size.** D2D's pixel-shader input signature is `(SV_POSITION, SCENE_POSITION, TEXCOORD0..N)` with one TEXCOORD per input. Six effects declared an incomplete signature, so the binding shifted and the parameter they called `uv0` received the **scene** coordinate instead of input 0's texel coordinate. Scene and texel coordinates coincide only while the content fills D2D's intermediate allocation -- which it does at the 1024px default -- so the defect hid completely until a source was smaller. Measured: a 256px `Gradient Generator` into an affected effect produced output whose left half was black and whose right half sampled **128px to the left**, a best-fit offset of `-128 px` at mean error 0.0001 -- exactly `-(512 - 256)/2`, the offset of centring 256px of content in a 512px intermediate. `Gamut Map` and `ICtCp Gamut Map`, which declared the signature correctly, tracked the source exactly on the same probe. Fixed in **Gamut Highlight, Nit Map, Split Comparison, ICtCp Round-Trip Validator and ICtCp Saturation**, plus one effect since removed -- six, not four: an adversarial review found the initial sweep had missed the last two, which declared `float2 uv : TEXCOORD` (bare semantic, float2) and so escaped the enumeration pattern. The Round-Trip Validator mattered most: its out-of-bounds `Load` returned 0, so `abs(back - color) * Gain` was also 0 -- the suite's one free correctness oracle was reporting a perfect round trip while reading transparent padding. It now reports the real FP16 residual. Verified at `+0 px` offset, with Nit Map's false-colour band transitions landing pixel-exact on their nit boundaries (x=32 at 20.3 nits, x=160 at 100.3 nits) and the 1024px baseline bit-identical (`2.5 -> 0.8678`).

  **This is the root cause of the long-standing "two-input pixel-shader effects render displaced" known issue**, and it was never really about two inputs. `Split Comparison` declared neither `SCENE_POSITION` nor `TEXCOORD1`, so it used a single scene coordinate to `Load()` **both** images; a two-input effect simply has twice the chance of one input not filling the intermediate. It now samples each input with its own normalized coordinate and takes its wipe geometry from `SCENE_POSITION`, and a self-comparison through it is offset `+0 px` at error 0.0000.

  Two consequences worth noting. **With the signature correct, `TEXCOORD` is normalized** -- so the four shaders moved from `Load(int3(uv0.xy, 0))` to `Sample(InputSampler, uv0.xy)`, matching the two that were always right, and anything genuinely needing pixel coordinates (a dither field, Split Comparison's wipe) now takes them from `SCENE_POSITION`. And the rule recorded in `CLAUDE.md` and `.github/copilot-instructions.md` -- *"D2D TEXCOORD is pixel/scene space, not normalized"* -- was a **description of this bug rather than of D2D**, and had been guiding new effects into reproducing it; both are corrected. The six source generators read no input and were relying on the same accident to obtain a scene coordinate, which is why they looked fine; they now declare `SCENE_POSITION` explicitly, with no behaviour change.
### Removed

- **`HDR Screenshot Tonemap (8bpc)` is no longer a built-in effect** (decision #101). It now lives outside this repository, as a side test effect loaded from saved graphs. A graph saved with it still loads and renders, because each node embeds its effect's HLSL. It just no longer appears in the Add Effect menu, and `graph_add_node` by that name fails. `ICtCp Gamut Boundary LUT` and Luminance Statistics' `WhiteErrorBudget` field remain. `Tests/RunIctcpMetrics.ps1`, `Tests/fixtures/adaptive_screenshot.json` and CI's "ICtCp metric gates" step moved out of the repo with it. The catalog is now **36** ShaderLab effects. Its test roles move to generic consumers: `ICtCp Round-Trip Validator.Gain` for the bound-consumer tests, and a new test-only pixel shader for lane 3 into a PS with a lookup input. That test measured `Max` = 80.0082 delivered identically through the texture and cbuffer paths.

- **`Gamut LUT Viewer`** (Analysis -> Tone Mapping; decision #113, [catalog](docs/effects/builtin-catalog.md)). Makes a gamut boundary table visible: a **slice map** (hue across, I up, each cell the boundary colour at that I and hue; a second table splits the view) or a **polar slice** (the Ct/Cp plane at one I, the in-gamut colours of table A dimmed, the boundary of each wired table as an anti-aliased curve, primaries marked at the rim). Both inputs are lookup inputs; each table's stamp gives its peak and I range, so the viewer takes no SdrWhiteNits, and a pin wired to something that is not a table draws magenta stripes. Tests check a slice-map pixel against the CPU ICtCp of the table's own texels (max abs error 1.1e-4 in ICtCp) and that the polar curve of each table sits at the texel radius. First look: the sRGB table at 20% of its I range shows a step in the boundary between the red and yellow corners (hue about 2.57 rad, radius 0.184 -> 0.163). It is real slice geometry, not a search miss: a CPU scan of the cube along each ray in 2e-4 steps finds the same last-inside radius to within 3e-4 on every column checked (45 columns, hue 2.07-2.62), including rays that leave the cube and re-enter.

  **Attribution follows the shape of the work rather than pretending every node is measurable.** A COMPUTE node reports its own dispatch -- exact and free, because each bridge dispatch is its own D3D11 submission. A D2D IMAGE node reports nothing, EXCEPT the node at the END of the chain, which carries the whole fused chain's draw cost. The state is the point: a blank figure could mean "cost zero", "cost real but attributed elsewhere", or "never ran", and those need different responses from the reader. Five states, each answering a different question -- **measured** (its own bracketed dispatch, or the chain end carrying the fused D2D chain that feeds it), **fused downstream** (a D2D image node whose cost is inside a downstream chain end's figure and cannot be split out without materialising it separately, which would change the workload being measured), **cached** (needed, but clean, so it served its cached result -- zero is the right answer, not "unknown"), **idle** (the evaluator skipped it because nothing consumes its output -- actionable: wire it up), and **cpu only** (a parameter node with no image output; there is no GPU work to attribute). - **Compute dispatches could silently write nothing, ~8% of the time, with an S_OK result — fixed by making compute submit as one call.** The runner issued each dispatch on the device's *shared* immediate context as a sequence: clear the output UAV, set shader, SRVs, UAVs, then `Dispatch`. That context is also where Direct2D draws — the render thread's and the UI thread's D2D contexts sit on the same device (deliberately; see P7) — and shader/SRV/UAV bindings are context state, not per-caller. `SetMultithreadProtected` serializes individual calls, not sequences, so another thread's work could land between the bind and the `Dispatch`. The clear takes its UAV as an explicit argument and always landed; the dispatch then ran with clobbered bindings and left the **cleared** texture behind. Surfaced by the gamut LUT's validity stamp: 2/24 re-dispatches came back all-zero with no MCP traffic involved, and temporary per-dispatch instrumentation showed the bad dispatches identical to the good ones — same bridge instance, same output texture, same 32×16 dims, same 24-byte cbuffer, `hr = S_OK`. Not LUT-specific: it is the compute path in general, and likely the "Scale outputs black" seen and passed over earlier (`Scale` reading 0/10 on the same trigger is not evidence of immunity at an 8% base rate).

  **The fix keeps compute out of Direct2D entirely.** `D3D11ComputeRunner` now records every command on its own **deferred context** and submits the whole dispatch — clears, bindings, `Dispatch`, the lane-3 publish, the staging copy — as a single `ExecuteCommandList`. One call is exactly what multithread protection makes atomic, so no lock is needed and the runner has no knowledge that D2D exists: a graph of pure compute nodes would never touch D2D's threading. The immediate context is touched for two single calls only, the submit and the readback `Map` (a deferred context cannot `Map` for read). `ExecuteCommandList` is passed `RestoreContextState = TRUE`, and that is load-bearing: with `FALSE` the runtime resets the immediate context afterwards, which would wipe D2D's half-built bindings if our submit landed mid-sequence — the same race pointed the other way. Result: **0/48** blank dispatches; accuracy bit-identical (LUT vs exact still mean 0.0061 / max 2.33 ΔE ITP); **no measurable cost** — throughput with GPU timing off, interleaved, 86.6 fps via command list against 80.8 fps call-by-call. (An interim fix held `ID2D1Multithread` across the runner call; it also measured 0/48, but it coupled compute to D2D's lock and was replaced.) `perf_compute_submit` switches the old path back on, for A/B only — it is racy. Two hypotheses were tested and rejected on the way: an empty cbuffer (ruled out by making the shader's writes independent of it — every blank stamped a hard 0, never the 0.0125 a zeroed cbuffer would give) and the MCP forced frame (blanks recurred at the same rate with no forced reads).

- **A test harness trap: fxc can take minutes and >5 GB compiling a shader that inlines `CubeBoundaryRadius` several times inside loops.** An in-kernel LUT-accuracy emulation did exactly that and was replaced by structural tests; accuracy is measured end to end instead. `[loop]` on the outer loops and a single call site were not enough.

- **A pixel-shader tone mapper was ~20x slower than it needed to be on any image wider than 2048 px, and the cause was not in the shader.** `CustomPixelShaderEffect::MapOutputRectToInputRects` answered every tile query with the WHOLE input rect rather than the tile it was asked about. That is free while Direct2D renders in one pass -- and past ~2048 px wide it tiles, so a whole-image answer makes it re-render the entire upstream chain once per tile. **Measured cliff, not a curve:** 2048x1280 **1.10 ms**, 2100x1280 **56.05 ms** -- 1.03x the pixels for 51x the time. Height is irrelevant (1280x2560 runs 1.02 ms; 2560x640, a third of the pixels, runs 51.25 ms), which is what named the axis. `TRIVIAL_SAMPLING` is declared, so output pixel N depends only on input pixel N and the sub-rect answer is the correct one; image inputs now get the queried rect and analysis pins keep the old answer. **Product case: the full 2880x1800 desktop-duplication graph (tone mapper + Luminance + Channel statistics, adaptive binding live) goes 12.5-15.0 fps -> 122-135 fps, ~10x**, reproduced across four A/B toggles. The tone mapper node itself goes **31.25 ms -> 1.90 ms**. Kept behind `Performance::IsSubRectInputDemandEnabled` (default on, `perf_subrect_demand` over MCP) because the whole-image answer is what shipped and a kill switch is cheaper than a revert.

  **Correctness was the whole question**, since this was tried once before and reverted -- the reason recorded then (previews showing only a sub-rect) was the `SCENE_POSITION` signature bug that has since been fixed. Verified three ways on a deterministic 2880x2880 `Gamut Source`, A/B'd against the legacy path on identical content: all **10 Luminance Statistics fields bit-identical over 8,294,400 pixels**; **512 floats at 8 scattered probe sites bit-identical**, four of them past the tile boundary; and a full capture differing in **5 pixels out of 4,194,304 by 1 code out of 255**, scattered across a 628x516 box rather than lined up at a boundary -- FP ordering in the downscale, the same character as the 1-ULP gamut early-out residual. Note the statistics alone would NOT have caught misplaced tiles (Min/Max/Mean/Median/P95 are permutation-invariant); the spatial checks exist for that.

  **This also relocates the bottleneck.** With the tone mapper at 1.90 ms, the frame is now 8.25 ms of which **deferredCompute is 6.17 ms** (Luminance 2.15, Channel 2.59, remainder the FP32 input pre-render) and draw is 1.91. The compute reductions are the next target, not the shader math.

  **A negative result worth recording**: before finding this, the tone mapper's own arithmetic was ablated stage by stage -- boundary search, chroma fit, whole gamut branch, and a floor variant with the entire ICtCp pipeline removed. **The floor saved 3%.** The 48-point boundary walk and the PQ `pow()` calls were never the cost at these sizes; measuring the shader would have optimised the wrong thing indefinitely. Two rig traps had to be cleared first: D2D output caching serves a clean node without re-executing it (so a node needs a per-frame dirty driver or it measures nothing -- 0.13 ms), and preview zoom decides how much gets shaded (at zoom >= fit D2D clips to the visible region; only below fit is the full intermediate rendered).

- **`perf_subrect_demand` must not tear down the effect cache.** The first version of that route called `GraphEvaluator::ReleaseCache` so the new mapping would be picked up. With the render loop unthrottled that reproducibly access-violated inside `d2d1.dll` (0xc0000005) -- three crashes before it was isolated by staging the variables: throttled + GPU timing + sub-rect ON clean, unthrottled + sub-rect ON clean, and the fault landing exactly on the route's cache teardown. The clear was never needed: the flag is read inside `MapOutputRectToInputRects` on every call, so `MarkAllDirty` + a forced render is sufficient. Stable across four toggles afterwards.

- **Unthrottled render loop, for benchmarking.** A *Unthrottled render loop (benchmark)* checkbox in the performance flyout and a `perf_render_mode` MCP tool (`Performance::SetUnthrottledRenderEnabled`, also reported by `perf_timings` as `unthrottled`). The render worker drops its 16 ms pacing wait, evaluates every tick regardless of dirty state, and the UI presents with vsync interval 0. Both caps existed to stop an editor pegging a GPU while someone reads the screen; neither protects correctness, and both cap a throughput measurement at the *display's* cadence rather than the pipeline's — the same way judging an HDR image on an SDR panel tells you about the panel. Expect tearing and fans; that is the intended trade for a development tool.

  **The measured result argues against the feature being the win it looks like, which is worth stating plainly.** On a clean graph (evaluator serving cached outputs) it takes the loop from 15.0 to **224.7 fps**. On the same graph made genuinely dirty every frame — `Clock → Exposure` between a 2880×1800 desktop-duplication source and a tone mapper plus two reductions — throttled and unthrottled both measure **5.0 fps**, because a 107 ms frame is already far past the 16 ms wait. **The pacing was never the limiter for real work**; it only ever hid an idle loop. Where the time actually goes (medians of 10 samples, D3D11 timestamps, **Debug** build): frame 54.3 ms = draw 31.7 (tone mapper 31.25 as chain end, which cross-validates the chain-end attribution against the Draw span) + deferredCompute 14.7 (Luminance 3.83, Channel 5.22, remainder is FP32 input pre-render) + evaluate 7.1.

  **Release numbers, and the conclusion holds there too.** Same rig, same graph, unthrottled, dirty every frame: the full chain (2880×1800 desktop duplication → Exposure → tone mapper + Luminance + Channel statistics) runs **5.0 fps in Debug and 13.5–15.0 fps in Release** — a ~3× build speedup, 200 ms → 67–74 ms per frame. Throttled vs unthrottled on Release is **15.0 vs 15.0**, exactly as in Debug: still GPU-bound, still nothing to do with the pacing. Stripping both statistics nodes leaves the tone mapper alone at **18.0 fps** (55.6 ms), so the two reductions cost ~11 ms together. GPU breakdown for the tone mapper alone (medians of 12): frame 58.6 ms, draw 50.3, evaluate 21.9, chain-end tone mapper 35.9 — **5.18 Mpx / 35.87 ms = 145 Mpx/s**. That figure is the concrete case for the PQ lookup-table work: per-pixel `pow()` in the PQ encode/decode plus the 48-point gamut boundary walk are what 145 Mpx/s buys. Caveats on the comparison: `framesSampled` publishes every 30 frames so a 20 s window is ±1.5 fps; GPU timing adds a Flush per span, so the breakdown run is slower than the untimed run it explains; and desktop-duplication content varies between runs (peak 480 vs 590 nits across two of these), which moves the gamut early-out hit rate and therefore the tone mapper's cost.

  Note the measurement method: `perf_timings.fps` is `1/totalUs`, the reciprocal of per-frame *work*, so it ignores the pacing wait entirely and reads ~35,000 on an idle throttled loop. Achieved throughput has to come from the monotonic `framesSampled` delta sampled at window boundaries **with no MCP traffic in between** — `WaitFor` is a cv predicate wait, so every MCP closure wakes the worker early and inflates the rate it is trying to measure.

  **A pure `WaitFor(0)` spin starved the UI thread and had to be fixed.** Each worker iteration takes `m_graphMutex` exclusively twice; with zero wait the next acquire follows the previous release by essentially nothing, and `std::shared_mutex` is an SRWLOCK, which is not fair — the UI thread's shared read for a canvas paint can lose indefinitely, so the app keeps rendering while its UI stops responding. A `std::this_thread::yield()` between iterations gives a ready thread on that processor its chance. Cost is ~10× on the clean-graph loop rate (a number that measures nothing) and zero on the GPU-bound path that matters.

- **An analysis node downstream of animated content dispatched exactly once, then reported plausible frozen numbers forever.** Dirty propagation was a *push*: walk the topological order once before evaluating and mark each dirty node's successors. That misses two things. (1) A property binding is an invalidation edge but not a graph edge -- a `Clock` has **no output pins and no edges at all**, driving consumers purely through bindings, so a push along edges leaves everything it animates marked clean. (2) A node can become dirty *during* the main loop, when `ResolveBindings` sees a bound value move; a pass that ran before the loop cannot know, and by the next frame the flag has been cleared, so the change propagates on **no** frame. Together: `needsCompute` was `dirty || bindingSourceQueued || (analysisOutput.fields.empty())`, with **no term for "my input image changed"**, so a statistics node fired on the one frame its fields were still empty and never again. Propagation is now a *pull* at each node's visit -- topological order guarantees every predecessor, edge **or binding**, has finished, so the "output changed this pass" set is final for all of them. Measured: the statistics node goes from **0/24 frames dispatching** to **20/20, at 1.899 ms each** -- a real 1.9 ms of per-frame GPU work that was previously invisible *and not being done*. All 340 tests pass.

- **`read_analysis_output` returned first-dispatch values at 200 OK, forever.** The route already tried to guarantee freshness -- clear the skip-readback flag, force a frame, restore -- but the readback happens *inside the node's dispatch*, so a forced frame in which the node is clean re-renders, dispatches nothing, and copies nothing back. Compounding it, the host's CPU-analysis interest set contains only the **GUI-selected node** and its binding sources, so over MCP (where nothing is selected) no dispatch ever carried `readback=true` after the first. The forced frame now dirties the node it is about to report on. The tell was arithmetic, not appearance: every field present and every number plausible, but changing the *source* node's `PatternSize` from 512 to 2048 left `Samples` pinned at 1048576, which is impossible for a live reduction. After: `Samples` tracks **262144 / 1048576 / 4194304** exactly, and `Mean` scales **274.55 -> 1098.20 -> 4392.80** across -2/0/+2 EV -- exactly 4.000x per 2 stops.

- **`Clock`'s play toggle worked from some MCP clients and not others, with no error either way.** `isPlaying` is a runtime field mirrored from a property, and the mirror accepted only a `std::bool`; a number or a string form was dropped while the route still answered 200. CLAUDE.md records that untyped MCP arguments arrive from Claude Code as JSON **strings**, so that was the common case, not the exotic one. Three separate defects, all fixed: (1) the mirror now coerces bool / float / int32 / uint32 / string; (2) the string vocabulary is shared with `set-property`'s pre-coercion, which previously recognised only `"true"`/`"1"` and folded **everything else to `false`** -- so `isPlaying: "yes"` silently meant *pause*, and so did a typo; the vocabulary is now `true/false`, `1/0`, `on/off`, `yes/no`, case-insensitive, and a word meaning neither is **rejected with a 400** rather than quietly picked; (3) play-from-the-end now **rewinds**, the way every transport control does -- with `Loop` off the tick clamps `clockTime` to the duration and stops again on the same frame, so pressing play on a finished clock was a silent no-op that read as a broken toggle. Verified across all eleven value forms: `true`/`1`/`"true"`/`"1"`/`"yes"`/`"on"`/`"TRUE"` all start it; `false`/`"no"`/`"off"`/`0` all stop it; `"banana"` and `""` are refused. Rewind measured: stops at 2.000, play returns 0.710 then 1.304.

- **`Clock` v2 gains `UpdateRate` (Hz), which gates the DIRTY rather than just the reported value.** At 0 it behaves as before: every frame is a tick and every consumer re-evaluates. Above 0, `Time`/`Progress` are quantised to 1/rate and consumers are dirtied only when that quantised value crosses into a new bucket — so the rate controls how often downstream work is INVALIDATED, not merely what number is reported. The tick and the evaluator quantise with the same rule, so a consumer woken for a tick never reads a value from between ticks.

  It exists to make "a frame" mean something specific when measuring. Driving a pixel-perturbing effect from the clock (Image -> Exposure<-Clock -> {Statistics, Tonemap}) gives a workload where every tick is a genuine full invalidation, which a static graph never is. Measured at 5.18 Mpx (Debug, GPU timing on): **12.9-14.0 ms per fully-invalidated frame** at 30 Hz and above, against **0.81 ms at 10 Hz**, where the clock emits slower than the renderer runs so most frames serve cached output. A 16x spread between "a frame" meaning redrawn and meaning recomputed -- precisely the ambiguity that made earlier frame-time figures impossible to interpret.

- **The FPS flyout's compute-dispatch count has always read 0.** `RenderFrameToOffscreen` took it from `GraphEvaluator::DeferredComputeCount()`, which reports the QUEUE depth — and `ProcessDeferredCompute` drains that queue before returning, so by the time the host could read it the answer was structurally zero on every frame the app has ever run. Replaced with `DispatchesLastFrame()`, incremented per actual `DispatchViaBridge` call and surviving the drain. Worth noting what the broken value was hiding: nothing. A static graph genuinely issues no compute dispatches — *Force continuous redraw* makes the worker re-evaluate every tick but dirties nothing, so an analysis node with unchanged input is never queued — which is why the zero looked plausible for so long. Related: the `deferredCompute` GPU span is opened and closed even on frames that dispatch nothing, and a span holds its last resolved value, so it reads ~0.002 ms (the cost of an empty pass) rather than the cost of the reduction on the frames that do run one.

- **Any ShaderLab custom PIXEL shader can now take analysis values as a GPU-resident texture.** A parameter marked `gpuBindable` and declared with the `SHADERLAB_GPU_BUFFER` / `SHADERLAB_PARAM` / `SHADERLAB_LOAD_PARAM` macros, so the host picks the mode per frame and compiles the matching variant. Verified end to end: with GPU bindings on, a consumer's output is **byte-identical to the cbuffer path** across 4096 FP32 components of real content — the value reaches the shader through a 1-row texture instead of a GPU→CPU→GPU round trip and nothing about the picture changes.

  **Pin layout**: pins `0..N-1` are the declared image inputs, pin `N+i` carries gpu-bindable parameter *i*. Pins are reserved for every gpu-bindable parameter whether or not it is bound, because the input count is fixed at effect registration and varying it would mean re-registering the CLSID whenever a binding changed. Two Direct2D behaviours had to be handled, and each produced a node that silently rendered NOTHING with no error anywhere: (1) D2D derives an effect's output rect from its inputs, so a 1×N analysis texture unioned into the bounds collapses them — `CustomPixelShaderEffect::SetImageInputCount` now excludes reserved pins from that union; (2) **D2D will not render a custom effect that has an unconnected input**, so reserved pins cannot be left null and are filled with a 1×1 dummy when unbound. The second one broke a consumer even with no bindings present, which is how it was caught — the unit suite was green while the actual render was empty.

  **Mode selection is per frame and degrades safely.** A parameter only goes texture-mode once the producer has actually published a bitmap; before the first compute dispatch there is none, so it stays cbuffer-bound and reads the CPU value. The readback-skipping pre-pass checks the same condition, so the CPU value is still refreshed on exactly the frames that need it — skipping on the merely-possible mode would starve the bootstrap frames, a silent wrong value rather than a slow one. Switching modes also requires a **distinct shader GUID**: Direct2D ignores `LoadPixelShader` for a GUID it already holds, so reusing the base GUID would keep running the cbuffer bytecode while the host believed it had switched.

- **Lane 3 is now reachable from the evaluator: the bridge delegates it, the binding predicate returns a MODE, and the producer's texture is wrapped as a D2D bitmap.** `CustomComputeBridgeEffect` forwards `IEngineComputeTexture` to its runner — the bridge is the only thing the evaluator can QI, because D2D's outer `ID2D1Effect` does not forward arbitrary IIDs to the impl, so every lane has to surface there even though none of them live there. `CanServeBindingViaGpu` now returns `GpuBindMode` (None / StructuredBuffer / Texture) instead of a bool, picked from what the CONSUMER can bind: a D3D11 compute effect controls its own dispatch and takes an SRV at any t-slot; a pixel shader cannot, so it gets the texture lane. During `ProcessDeferredCompute` a texture-mode binding calls `RequestAnalysisTexture()` on the producer BEFORE the dispatch that fills it, and afterwards the texture is wrapped via `CreateBitmapFromDxgiSurface` and cached per producer — as a VIEW, not a copy, so the wrapper is reused until the underlying texture is replaced rather than rebuilt every dispatch. The wrapper uses `R32G32B32A32_FLOAT` to match (FP16 would quantise a 620-nit peak to half-nit steps, and avoiding exactly that loss is the point of the lane) and `D2D1_ALPHA_MODE_IGNORE` (these are data, not colour — a premultiplied interpretation would let D2D scale the value channel by alpha).

  **`IsGpuBindModeWired` is deliberately separate from the mode**, and returns false for Texture until the input-wiring step lands. The readback-skipping pre-pass consults the WIRED predicate, never the mode: trusting a lane the evaluator does not actually establish would leave the consumer sampling a texture nobody filled while its CPU fallback quietly stopped being refreshed — a silent-wrong-output bug rather than a slow one. Lane-3 wrappers are dropped in `ReleaseCache` alongside the bridges whose textures they alias.

- **A compute-analysis node can now publish its results in three shapes, and materialises only the ones the graph consumes.** Lane 1 is the existing `StructuredBuffer` SRV for a COMPUTE consumer; lane 2 is the CPU readback; **lane 3 is new** — `IEngineComputeTexture` publishes `Result[]` as a 1×N RGBA32F texture, the only GPU-resident route a Direct2D PIXEL shader can consume. Lane 3 is strictly opt-in: until a consumer calls `RequestAnalysisTexture()` the texture is never created, the copy shader is never compiled and no dispatch runs, so a graph with no pixel-shader consumer pays nothing. A buffer cannot be `CopyResource`d into a texture (D3D will not convert dimensions), so the copy is a one-line compute pass over N texels — the cost is the dispatch, not the work. It runs after the main dispatch unbinds its UAVs, because the copy reads the result buffer as an SRV and D3D silently drops one of the two views if both are bound at once. Ten tests pin the contract: opt-in by default, `E_NOT_VALID_STATE` before the request, correct shape, **texels equal to the structured buffer** (a copy that quietly reordered a field would surface far downstream as a shader reading the wrong statistic), and lanes 1 and 2 undisturbed.

  **The bytecode cache key now carries TWO bits per gpu-bindable parameter instead of one**, so a parameter can be cbuffer-bound (0), SRV-bound (1) or texture-bound (2) rather than merely on/off. 16 params fit in the existing `uint32_t`; beyond that the tail stays cbuffer-bound, which is always correct if slower. Existing mode-1 routing is unregressed (the Phase 8 GPU-binding tests still pass).

- **`shaderlab_params.hlsli` gains binding mode 2: analysis values smuggled through a Texture2D effect input**, so a Direct2D PIXEL shader can take a GPU-resident binding for the first time. Modes were 0 (cbuffer) and 1 (StructuredBuffer SRV); mode 1 is unavailable to a pixel shader because D2D maps a transform's INPUTS to t0, t1, ... and will not bind an arbitrary SRV, and the obvious alternative is a dead end — `ID2D1EffectContext::CreateResourceTexture` and `ID2D1ResourceTexture::Update` both take `const BYTE*` CPU memory, so routing an analysis result through one would reintroduce the readback the binding exists to remove. Mode 2 declares `Texture2D<float4> _SLTex_<name>` at the input's t-slot and fetches with `Load(int3(index, 0, 0))` — `Load`, not `Sample`, since a sampler would filter neighbouring FIELDS together. `ShaderLabAnalysisField` / `ShaderLabAnalysisTexel` helpers give an effect the whole row when it wants more than one value. **All three modes compile from identical source text**, so the host can change binding strategy without the effect being re-authored; tested at `ps_5_0` specifically, since the StructuredBuffer form also compiles for `cs_5_0` and so could not prove the pixel-shader path.

### Known issues

- **Analysis values still cannot reach a PIXEL-shader parameter without a CPU round trip.** `CanServeBindingViaGpu` (`GraphEvaluator.cpp:1798`) requires the consumer to be a D3D11 *compute* effect — only `CustomComputeBridgeEffect` can wire upstream SRVs at t-slots — and a tone mapper written as a pixel shader is not one, so `SourcePeakNits <- Max` is CPU-served by construction and forces the statistics readback even now that the budget expression is gone. Two further things block it: the engine-wide GPU-bindings flag defaults OFF and **the GUI never enables it** (`SetGpuBindingsEnabled` is called only from headless), and the obvious fix does not work — `ID2D1EffectContext::CreateResourceTexture` and `ID2D1ResourceTexture::Update` both take `const BYTE*` **CPU memory**, so a resource-texture binding would require the very readback it is meant to remove. The viable route is D2D-native: Direct2D maps effect inputs to `Texture2D` at t0, t1, ... so the statistics node should expose its fields as a small **image output** wired into a reserved input slot on the consuming pixel shader, which stays entirely on the GPU. Designed, not built.

- **GPU timing, because every performance number this project had was measuring the wrong thing.** `perf_timings` and the FPS flyout were CPU wall-clock wrapped around Direct2D calls — and D2D submission is *asynchronous*, so those figures time command *recording*, not GPU execution. For shader work the two are unrelated: a still frame reported **114 fps** while one re-render of the same graph took hundreds of milliseconds, and a perf sweep built on them returned ±50% run-to-run variance with several *negative* costs. New `Rendering/GpuTimer` issues D3D11 timestamp + disjoint queries from a 4-deep ring so results never stall the pipeline, and is surfaced everywhere timings already were: `perf_timings` gains `gpuFrameMs`/`gpuEvaluateMs`/`gpuDeferredComputeMs`/`gpuDrawMs` plus `gpuAvailable`/`gpuEnabled`/`gpuFramesResolved`/`gpuDisjointDrops`; a new `perf_gpu_timing` tool toggles sampling (catalog 39 → 40); the FPS flyout grows a GPU block that says plainly when timing is off and why the CPU numbers above it cannot answer a shader question; headless gains `--gpu-timing` and a `gpu-bench` script op. **Off by default** — closing a span around D2D work needs a `Flush`, which breaks batching and perturbs the frame being measured — and **enabling it also makes the render worker evaluate continuously**, because the worker is gated on `hasDirty || m_needsFitPreview || m_forceRender || hasOutputWindows` and a static graph dirties nothing. Without that, the timer opens exactly ONE frame, the 4-deep ring never retires, and every span reads 0.00 ms — which looks like a broken timer rather than an idle renderer. (A `Clock` node in the graph achieves the same thing by hand.)

  **Three traps had to be designed around, each of which silently reads as "the shader is free".** (1) D2D evaluates an effect chain *lazily at DrawImage*, so a bare evaluation rasterizes nothing — `gpu-bench` draws the node into a full-size offscreen target. (2) D2D shades only the pixels asked for, so timing a render and then reading a 2×1 `pixel-region` measures an almost-empty raster. (3) A timestamp closed right after a D2D call lands before D2D has emitted any work, so the span reads ~0; the `End()` overload that takes a device context flushes first. Two bugs in the timer itself were found the same way: `GetData` with `DONOTFLUSH` never retired under vsync (`framesResolved` stuck at 0, reading as "the GPU did no work"), and a `BeginFrame` sitting above two early `return`s wedged the ring permanently on one slot.

  **A saved graph freezes its shader, which invalidated a whole round of measurements.** `graph_save_json` embeds each node's `hlslSource` — and `GetColorMathHLSL()` is prepended at registration, so the *entire* shader is captured into the file. Benchmarks run against a saved graph therefore replay a frozen shader and every engine rebuild is invisible: source edits appeared to change nothing at all, while `GamutStrength` (a runtime uniform) moved the number, which reads exactly like "that code is not the bottleneck". Benchmark graphs are now built from the effect registry via `/graph/add-node`. **Measured baseline** (GPU time, 5.184 Mpx source, Debug): tone mapper alone **5.83 ms**; with the per-frame `Luminance Statistics` reduction — the video path — **10.29 ms**, i.e. **16.5 ms at 4K, right at the 60 fps line**, not the 3–5 fps a wall-clock reading had suggested.

- A provable-identity gamut early-out (2.6-2.9x) in the since-removed HDR screenshot tone-mapping effect (decision #101; its history is kept out of tree).

- **The 8-bit dither ran at half the amplitude that makes the quantiser mean-preserving, and the test that should have caught it sat on the one input value that cannot.** `DitherQuantize` scaled the noise by `0.5 * strength` while its own comment declared `1.0 = standard TPDF`, so the shipped default offset by ±0.5 LSB rather than the full ±1. A dither is not decoration: its specification is that the mean output code equals the input value, and at half amplitude the noise cannot reach the rounding boundary for most fractional parts, so the rounding stays very nearly deterministic. **Measured over a 128² field, the residual bias is ~0.197 codes at every fractional part except exactly 0.5** — targets 254.2083/254.7083/250.30/200.75 give −0.1974/+0.1972/−0.1969/+0.1973, against <0.001 at full amplitude. For a saturated red at encoded 254.7083 the 254/255 split was 9.5/90.5% where mean preservation needs 29.2/70.8%. Fixed to full amplitude (`RotatedIgnDither(p) * strength`). **Why it survived:** the spread test probed `187.5/255`, an *exact half-code* — the single fractional value in 256 where the rounding decision is symmetric and therefore mean-preserving at any symmetric amplitude. A test input sitting on a symmetry point silently waives the property it appears to assert. Replaced by a mean-preservation test at two non-half targets, verified to fail on the pre-fix shader and pass after.

  **Follow-on: `TriangularDither` is not triangular, and is renamed `RotatedIgnDither`.** The two samples are not independent. Offsetting `p` by `5.588238` shifts `dot(p, k)` by `0.407649`, and the `×52.9829189` amplification turns that into a pure rotation of the first sample — `n2 == frac(n1 + 0.59844)` or `frac(n1 + 0.61552)` depending on whether the inner `frac()` wraps, with every sample taking one of those two branches (62%/38% over a 64² lattice, 0% neither). Their sum is therefore a two-slope sawtooth in `n1` whose slopes each map uniform `n1` to a *uniform* output, on ±(1−r) and ±r at density 0.5. Superposing those — a superposition, not a convolution — gives a **stepped** density: flat at 1.0 across the plateau, flat at 0.5 on the shoulders, vertical risers, no linear ramps. It is therefore not trapezoidal either; a trapezoid needs a convolution of two *independent* uniforms. Measured support ±0.6155 and variance 0.0945 against ±1 and 1/6 for a real TPDF, with the two-uniform model predicting the measured density to within 0.005 everywhere (WARP agrees with the CPU model). **Renamed to `RotatedIgnDither`** — named for its construction, which three lines of code verify, rather than for a distributional property that turned out to be false. **Left as it is deliberately:** the trapezoid is symmetric and mean-preserving, which is the property that matters, at 44% less noise variance than a true TPDF (~0.31 vs ~0.41 codes RMS); what a real TPDF adds is *constant* error variance, which is worth having in audio and marginal in a still image. Pinned by a test asserting the measured variance and support, so decorrelating the samples later is a visible, deliberate change rather than a silent one.

- **A compute node consuming another compute node served the previous evaluation's pixels — a silent one-mutation lag.** `EvaluateNode` pre-renders each image-producing compute node's upstream input into an FP32 bitmap during `Evaluate`, deliberately, so the capture happens "while properties are fresh" and D2D's own caching can't hand back stale data. But `Evaluate` runs *before* `ProcessDeferredCompute` dispatches anything, so when the upstream is itself a deferred compute node, that pre-render captures the producer's **previous** output texture. The consumer then renders from it, one full evaluation behind, silently and at HTTP 200. Measured on `Gradient Generator → ICtCp Tone Map → ICtCp Highlight Desaturation`, sweeping `TargetPeakNits`: the consumer read `1.400438 / 1.400438 / 0.772682` where the producer read `1.401232 / 0.772924 / 2.435596` — each consumer value is the producer's *prior* one. This is worse than a crash because every individual reading is plausible; only a sweep reveals it. It also hit the measurement instruments themselves — `Delta E Comparator` and all three Statistics nodes are `D3D11ComputeShader`, so any graph putting a compute effect on a comparator pin was grading the previous mutation. `ProcessDeferredCompute` now tracks which nodes it dispatches in the current pass **and everything downstream of them**, and for any input fed by that set discards the stale `Evaluate`-time snapshot and re-renders through the shared pre-render path — inside the draw session, after the producer ran. `m_deferredCompute` is built in topological order, so the producer is always already dispatched; `preRenderShared` memoizes per pass, so fan-out still costs one render per distinct image. Verified end to end: consumer now reads `1.400438 / 0.772682 / 2.434046`, tracking its producer in the same render; a 3-deep compute chain and a fan-out branch both track; `Delta E Comparator` self-comparison stays exactly 0.000000 and a repeated parameter setting reproduces its earlier reading exactly. The transitive part was missed on the first attempt and caught by adversarial review: checking only the IMMEDIATE producer fixed `compute -> compute` while leaving `compute -> pixel shader -> compute` lagging, because the middle node is not in the deferred set even though its D2D output resolves through an undispatched producer. Measured on `ICtCp Tone Map -> Nit Map -> ICtCp Highlight Desaturation`: the consumer read `1.400438 / 1.400438 / 0.772682` against an input of `1.401232 / 0.772924 / 2.435596`. Data-only consumers never had it, since they do not pre-render at all -- which is exactly why the direct-edge test passed. Pinned by six new tests (`TestComputeChainFreshness`, both shapes) which dispatch **once** per sweep — the existing two-dispatch `runTwoPass` helper masks the lag by giving the consumer a second chance to catch up — and which were confirmed to fail with the fix disabled and pass with it enabled. **303/303 tests pass.**

- **Headless evaluated inside its own D2D draw session, so every compute node in a mutated graph read black or served stale analysis.** `GraphEvaluator::Evaluate` pre-renders each compute node's upstream input via `PreRenderInputBitmap`, which opens its **own** `BeginDraw`/`EndDraw`. Both headless entry points wrapped their `Evaluate` passes in an outer `BeginDraw`, so that inner draw was nested and failed with `D2DERR_WRONG_STATE` (`0x88990001`) — leaving the pre-render bitmap at its `Clear` value and the compute shader reading black, with no error recorded anywhere. Only re-queued nodes take the `Evaluate`-side pre-render path, which is why the symptom appeared *after* the first `/graph/set-property` rather than on the initial frame, and why it looked like a property-plumbing bug. Two failure modes, and the second is worse: a node dispatched before the break serves **stale-but-plausible** numbers forever (`m_sharedPreRenderCache` reuses the same bitmap across frames), while one that never succeeded reads zeros. Measured on `Gradient Generator → Luminance Statistics` with an `ICtCp Tone Map` connected to the same source: `Max` pinned at **319.84** across a source change that should have taken it to **719.38**, with two `PreRenderInputBitmap` failures on stderr; the tone map's own output went to `(0, 0, 0)`. Fix is the split `MainWindow::RenderFrameToOffscreen` already used — `Evaluate` **outside** the session, `ProcessDeferredCompute` **inside** it (it calls `dc->DrawImage` internally and silently no-ops outside one), and the post-dispatch sweep run under `SetDeferredComputeFrozen` so it cannot re-queue a compute node and re-enter the nested path. Applied to both `RunScript`'s `runEval` and `RunRender`'s `--output` path. Verified by controlled experiment: restoring the old shape reproduces the stale `319.84` and prints the two nested-draw failures; the fixed shape tracks to `719.375 / 359.99` with silent stderr. 300/300 tests pass and an unrelated tone-map probe is bit-identical (`2.5 → 0.8678`). **Any headless `--pixels`, analysis, or golden-image baseline captured through a graph containing a connected compute node should be re-taken.**
- **The three nested-`BeginDraw` helpers no longer fail silently.** `PreRenderInputBitmap` discarded its `EndDraw` HRESULT and returned the unrendered bitmap; `ReadHistogramOutput` discarded it entirely; `ReadCustomAnalysisOutput` checked it but returned without recording anything, so a broken session produced plausible-looking stale analysis with no diagnostic in `runtimeError`, `analysisOutput`, or any log. All three now report to stderr with the node id and HRESULT, the two node-scoped ones set `EffectNode::runtimeError` (which surfaces in the Properties panel and `graph_get_node`), and `PreRenderInputBitmap` returns `nullptr` rather than handing back a bitmap it did not draw into. - **`Working Space` nodes created after a display profile was applied kept their 80-nit defaults in the headless host.** `UpdateWorkingSpaceNodes` — the engine helper that mirrors the active display profile into the node's 14 analysis fields — is only called from the `/display/profile` and `/display/profile/clear` routes, which sync *on change*. - **`Soft Compress` mode on `ICtCp Gamut Map` (v11)** — ACES-RGC-style soft roll-off. The new mode instead remaps each pixel's chroma radius through `SoftCompressDistance(d, SoftThreshold, SoftLimit)` in the shared color-math library: identity below `SoftThreshold`×boundary, then a C1-continuous power-curve knee (`KneeHardness` = the ACES `p`: 1.0 is exactly Reinhard, higher tracks identity longer and corners harder; default 1.2 per the ACES RGC) whose scale is solved so `SoftLimit`×boundary lands exactly on the shell — reserving a headroom band just inside the gamut so out-of-gamut colors stay ordered instead of clipping. Also touches legal near-boundary colors (the inherent trade), preserves hue (radial in Ct/Cp) and luminance (Y renormalization), and samples the boundary per-I-level like the other modes. New `BoundaryRadius` polygon-ray helper; the three knee params are `visibleWhen` mode 3. Six contract bench tests in `GamutTests.cpp` pin identity/anchor/C1-slope/monotonicity/softness/hardness-ordering (including the p=1 Reinhard closed form).
- **`KneeNits` on both ICtCp tone mappers (v13)** — BT.2390-EETF-style knee: bit-exact identity at or below `KneeNits`, curve only above, C1-continuous at the knee; `0` (default) reproduces the previous expand/compress-from-black curves exactly. Motivated by measured mixed-content failures (an image whose SDR chunk is presentation-referenced while other regions are scene-referred HDR): the classic forward curve washed a 241-nit SDR region to 79 nits, and the classic inverse curve clamped 113–241-nit content uniformly to the 1000-nit peak. The primary workflow this enables: **HDR screenshot of a mixed SDR/HDR desktop → faithful SDR image** via `ICtCp Tone Map (Knee≈0.7·W, Source=peak, Target=W)` → `White Level Adjustment (W→80)` → sRGB save, where `W` is the SDR-chunk white (the OS slider level). On the inverse mapper the knee supersedes the `DiffuseWhiteNits` lift (identity-below-knee is the contract; the lift stays for the knee-less mode).

## [1.5.0] - 2026-05-06

The "headless agent fidelity" release. Every health & scalability phase from the eight-phase plan landed (some partially), the engine grew a host-agnostic ABI + a console host (`ShaderLabHeadless.exe`), the MCP HTTP server moved out of `MainWindow.xaml.h` into the engine DLL with a sink-and-event-hook architecture so MCP-driven graph mutations take the same UI code path the user does, and a JSON `--script` batch mode lets agents run parameter sweeps without a logged-in user. Also: graph viewer DPI fix, two new live-capture sources (DXGI Desktop Duplication, Windows Graphics Capture), and a few user-visible behavior tweaks called out below.

### Added

- **`ShaderLabHeadless --script PATH --script-output PATH`** — JSON batch mode for parameter sweeps. Each step is either a raw `{method, path, body}` HTTP shape or a `{op: ...}` shorthand (`set-property`, `image-stats`, `pixel-region`, `capture-node`, `get-graph`, `get-node`, `analysis`, `render`). Output is a structured JSON document with one `{step, method, path, status, body}` entry per operation; bodies are parsed JSON when possible. Smoke test asserts a Luminance=80→200 set-property → image-stats sequence produces a 2.5× luminance mean ratio end-to-end, exercising set-property → dirty propagation → evaluator → GPU reduction → JSON response across the whole stack.
- **`IEngineCommandSink` event hook architecture (8 hooks).** `OnNodeAdded`, `OnNodeRemoved`, `OnNodeChanged`, `OnGraphCleared`, `OnGraphLoaded`, `OnGraphStructureChanged`, `OnCustomEffectRecompiled`, `OnDisplayProfileChanged`. The GUI's `MainWindow::GuiEngineCommandSink` overrides each hook to call the same UI methods MainWindow uses on native user interactions (`AutoLayout`, `RebuildLayout`, `PopulatePreviewNodeSelector`, `UpdateStatusBar`, `MarkAllDirty`, `CloseOutputWindow`, `PopulateAddNodeFlyout`, `ResetAfterGraphLoad`). The headless host leaves each hook as the default no-op. **MCP-driven mutations are now indistinguishable from native UI interactions** at the host level — an agent calling `/graph/add-node` triggers exactly the same downstream UI code path as the user clicking the toolbar.
- **Engine MCP routes — 21 of 21 engine-pure routes migrated to the engine DLL.** New `Engine/Mcp/EngineMcpRoutes.{h,cpp}` owns: `/registry`, `/effect/hlsl/<id>`, `/effect/compile`, `/graph/add-node`, `/graph/remove-node`, `/graph/connect`, `/graph/disconnect`, `/graph/set-property`, `/graph/load`, `/graph/clear`, `/graph/bind-property`, `/graph/unbind-property`, `GET /graph` (incl. `/graph/save`, `/graph/node/<id>`), `/custom-effects`, `/analysis/<id>`, `/render/image-stats`, `/render/pixel-region`, `/render/capture-node`, `/display/profiles`, `/display/profile`, `/display/profile/clear`. The remaining 16 routes in `MainWindow.McpRoutes.cpp` are intentionally app-side (UI-coupled or host-specific). `MainWindow.McpRoutes.cpp` shrank from **2670 → 1478 lines (-44.6%)**.
- **Engine helpers extracted (reusable across GUI + headless).** `Rendering/PixelReadback.{h,cpp}` (FP32 RGBA region readback), `Rendering/CaptureNode.{h,cpp}` (D2D + WIC PNG encode of any node), `Rendering/WorkingSpaceSync.{h,cpp}` (Working Space parameter node refresh), `Effects/ColorMath.cpp` (shared HLSL color math library).
- **Engine ABI versioning.** New `SHADERLAB_ENGINE_ABI_VERSION` constant in `EngineExport.h` (currently 1) plus C-linkage `ShaderLab_GetAbiVersion()` exported from the engine DLL. `MainWindow::MainWindow` calls it on startup and aborts with a friendly message-box if the loaded DLL's reported version doesn't match the headers we compiled against — catches the "you forgot to redeploy the engine" class of confusion that otherwise manifests as obscure runtime failures. Independent of `Version.h::VersionMajor` (the app version) and `Version.h::GraphFormatVersion` (the JSON schema). Bumped manually whenever a public engine symbol's signature or behavior breaks consumers.
- **`Bootstrap.ps1` at repo root + CI bootstrap-smoke job.** One-command setup for fresh clones: runs `scripts/EnsureDevCert.ps1` + `scripts/EnsureExprTk.ps1` + NuGet restore, with optional `-Build` flag for a Debug|x64 smoke build. CI runs Clean clone → `Bootstrap.ps1 -Build` → tests on every PR. Catches onboarding-cliff regressions automatically.
- **HLSL math test bench (51 tests).** `Tests/ShaderTestBench.{h,cpp}` D3D11 compute harness + 51 tests across 5 categories (transfer functions, color matrices, Möbius/Reinhard tone curves, ΔE, gamut boundaries). Surfaced two real bugs: `PQ_InvEOTF` API misuse (nits vs normalized) and `DeltaE2000` NaN when `C2 == 0`.
- **Engine-side `Rendering::ReadPixelRegion` helper + `ShaderLabHeadless --pixels` mode.** Status enum (`Success`/`NotFound`/`NotReady`/`InvalidRegion`/`D2DError`). `--pixels x,y,w,h` writes either packed binary (`uint32 W` + `uint32 H` header + `float[W*H*4]` row-major) or `.csv` rows. Bypasses PNG / HdrToneMap entirely — full-accuracy scRGB for MCP-driven dE sweeps and quantitative analysis.
- **D2D HdrToneMap pre-pass in ShaderLabHeadless** (default-on). New `--input-peak-nits N` (default 1000), `--output-peak-nits N` (default 80 = SDR), `--no-tonemap` flags. Inserts `CLSID_D2D1HdrToneMap` into the render path before PNG encode so HDR scRGB content above 1.0 doesn't silently saturate to 255.
- **DXGI Desktop Duplication source + Windows Graphics Capture source** (Zachary's contribution, integrated). New entries in the Add Node ▸ Source flyout: a "DXGI DuplicateOutput" submenu listing each enumerated adapter/output, and "Windows Graphics Capture..." opening the standard WinUI graphics capture picker. Both render a live capture stream into the graph as scRGB FP16 frames.
- **Graph viewer DPI scaling fix** (Zachary's contribution, integrated). The graph SwapChainPanel now sizes its backbuffer to physical pixels via `CompositionScaleX/Y` with a `CompositionScaleChanged` handler. Fixes blurry/aliased nodes on high-DPI monitors.

The "always keep at least one Output node" protection has been removed; the render path tolerates an output-less graph fine (no nodes are "needed" so evaluation no-ops until you add a new Output). ### Fixed

- **DXGI Desktop Duplication / Windows Graphics Capture sources don't update past the first frame.** `SourceNodeFactory::TickAndUploadLiveCaptures` was defined but never called. Wired into `OnRenderTick` so live captures advance every frame; the helper marks captured nodes dirty, which trips the existing `needsEval` gate and triggers the rest of the render pipeline.
- **`DeltaE2000` NaN when one input has C == 0 (a == b == 0).** Found by the Phase 2 test bench against Sharma reference pair 6. `atan2(0, 0)` is implementation-defined and was propagating NaN through `hp_avg = h1p + h2p`. Guarded both `h1p` and `h2p` with a `Cnp < 1e-10 ? 0.0 : atan2(...)` check. Effect version `Delta E Comparator` 3 → 4.

## [1.4.1] - 2026-05-05

### Added
- **`OutputMode` parameter on the `Delta E Comparator` effect** (effectVersion 2 → 3). Two modes: `0 = Heatmap` (default — Turbo colormap, prior behavior) and `1 = Grayscale dE`. Grayscale mode writes `saturate(dE / MaxDeltaE)` to all three RGB channels, which makes a downstream `Luminance Statistics` node read true mean/p95/max color-difference values directly off the GPU — no CPU pixel readback required. Enables live in-graph dE telemetry while sweeping a tone-mapper's parameters: bind / drive any input, watch the mean dE field update in the Properties panel each frame.
  - Read all uniforms unconditionally before the mode branch (mirrors gotcha #2 in CLAUDE.md so D3DCompile can't strip `OutputMode` if the agent only ever uses heatmap mode).

### Changed
- **`README.md` decision log #52** updated with a cleaner empirical result on `Colors of Journey_1002.mp4`. Earlier entry said `ToneLift ≈ 0.6` matches D2D within ~10 %; that was matching the dark/mid *luminance levels* visually. A proper CIEDE2000 fidelity-to-source measurement (using the new Grayscale dE + LumStats live-readout pipeline) shows the *color-accuracy* optimum is `ToneLift ≈ 0.30`, with mean dE 9–32 % lower than D2D HDR Tone Map across three frames spanning 0.5 → 124 nit p95 source brightness. The default of `0.0` (pure peak compression, neutral) is retained.

## [1.4.0] - 2026-05-05

### Removed

The `Working Space` parameter node + property bindings (decision #51) are now the only path for tracking the active display profile from a graph.
  - **Effects converted** (12, all schema-broken — bumped `effectVersion`): Gamut Highlight, Luminance Highlight, CIE Chromaticity Plot, Gamut Source, Gamut Coverage, Gamut Map, ICtCp Gamut Map, ICtCp Boundary, ICtCp Tone Map (HDR → SDR), ICtCp Inverse Tone Map (SDR → HDR), ICtCp Highlight Desaturation, Luminance Statistics.   - **Replacement pattern**: each affected effect's gamut/range enum gains a `Custom` entry as the last index (existing static modes — `sRGB`, `DCI-P3`, `BT.2020`, etc. — are kept for strict-mode analysis without wiring 3 binds), and the host-managed primaries are promoted to first-class bindable `Float2` parameters (`RedPrimary`, `GreenPrimary`, `BluePrimary`, plus `WhitePoint` where applicable) gated by `visibleWhen "TargetGamut == 3"`. CIE Chromaticity Plot is the exception — its monitor primaries were always implicit, so the new `Float2` params are unconditional. Effects that consumed `(Ws)SdrWhiteNits_hidden` (ICtCp Tone Map / Inverse Tone Map / Highlight Desaturation / Luminance Statistics) drop the hidden field entirely; their existing numeric peak-nit parameter (`TargetPeakNits` / `SourcePeakNits` / `ClipNits`) becomes the single source.

  - **Saved-graph breakage** (accepted, no other users yet): old graphs loaded from `.effectgraph` files keep stale `_hidden` properties in their `node.properties` map, but the shader cbuffer no longer references them and they're filtered out of the Properties panel + pin list (decision #35 retained for exactly this reason). Old `Working Space` enum-mode selections clamp to an invalid index → user re-picks. No graph format version bump.

### Added
- **HDR / gamut / tone-mapping MCP tool suite (10 new, 27 → 37 total).** Round 2 of the agent-driven HDR workflow: simulate any display profile, capture any node's output, drive the preview view, run GPU stats, sample pixel grids, and inspect HLSL — all without mutating UI state.
  - `list_display_profiles` — GET `/display/profiles`. Returns 7 built-in presets (sRGB SDR, sRGB 270, P3 600, P3 1000, BT.2020 1000, BT.2020 4000, AdobeRGB) + the active live/simulated profile + `isSimulated` flag. Full caps in JSON: hdr/peak/sdrWhite/min/maxFullFrame nits, primaries (CIE xy), gamut id.
  - `set_display_profile` — POST `/display/profile`. Apply a simulated profile via exactly one of `{preset, presetIndex, iccPath, custom}`. `custom` accepts the full `{name, hdrEnabled, sdrWhiteNits, peakNits, minNits, maxFullFrameNits, primaryRed, primaryGreen, primaryBlue, whitePoint, gamut}` schema; missing fields fall back to sane defaults. Drives `MainWindow::ApplyDisplayProfile`, marks the graph dirty, forces the next render frame.
  - `clear_simulated_profile` — POST `/display/profile/clear`. Reverts to the live OS-reported profile.
  - `render_capture_node` — POST `/render/capture-node` body `{nodeId, inline?}`. Captures any node's resolved image as PNG without touching `m_previewNodeId`. Forces a render frame first so dirty nodes evaluate. With `inline=true` returns MCP-native image content (`type:"image"`, `mimeType:"image/png"`); without it, writes a unique `%TEMP%\shaderlab_node_<pid>_<seq>.png` and returns the path. Disambiguates not-found (404) vs not-ready (409 + `notReady:true, reason:"dirty"|"missingInputs"`).
  - `preview_get_view` / `preview_set_view` / `preview_fit_view` — symmetric with the graph view tools but for the preview pane. zoom is clamped to [0.01, 100.0] (matches the wheel-zoom range, much wider than the graph view's [0.1, 5.0]); pan is unclamped. `preview_set_view` returns post-clamp values.
  - `image_stats` — POST `/render/image-stats` body `{nodeId, channels?, nonzeroOnly?}`. Per-channel min/max/mean/median/p95/sum + nonzero counts, GPU-reduced on a fresh FP32 render of the target. Defaults to luminance + R + G + B + A; pass `channels:["luminance"]` to skip the others. Backed by a new `GraphEvaluator::ComputeStandaloneStats(dc, image, channels, nonzeroOnly)` so MCP doesn't have to own a separate reduction instance or mutate the graph for diagnostics.
  - `read_pixel_region` — POST `/render/pixel-region` body `{nodeId, x, y, w, h}`. Reads a small w×h region of FP32 RGBA pixels (scRGB linear-light) row-major as a flat float array. Capped at 32×32 (1024 pixels) and per-axis at 64; oversize requests fail 400 with the cap quoted so agents can chunk. Out-of-bounds rects clip to the image; empty after clip → 404.
  - `effect_get_hlsl` — GET `/effect/hlsl/{nodeId}`. Reads a custom-effect node's HLSL source, parameter list, compile state, last runtime error. For ShaderLab library effects also returns `isLibraryEffect:true` + `shaderLabEffectId`/`shaderLabEffectVersion` so the agent knows what's read-only. Non-custom nodes return `hasCustomEffect:false` (200, not 404) so the agent can probe any node.
- **Graph snapshot + view-control MCP tools** (4 new). AI agents can now request a PNG of the live node-graph editor view and steer its pan/zoom exactly the way a user would. Implementation lives in `MainWindow::CaptureGraphAsPng()`, `MainWindow::FitGraphView()`, and `NodeGraphController::ContentBounds()`. The shared `MainWindow::RenderGraphScene()` helper drives both the live render tick and the off-screen snapshot so the two never drift.
  - `graph_snapshot` — POST `/graph/snapshot`. Always writes a unique `%TEMP%\shaderlab_graph_snapshot_<pid>_<seq>.png`. With `inline=true`, the JSON-RPC response carries MCP-native `content[].type=image` + `mimeType=image/png` so the agent gets the bytes directly. Snapshot renders the current pan/zoom at the live swap-chain panel size — same dimensions the user sees.
  - `graph_get_view` — GET `/graph/view`. Returns `{zoom, panX, panY, viewportW, viewportH, contentBounds, zoomLimits}`.
  - `graph_set_view` — POST `/graph/view` body `{zoom?, panX?, panY?}` (any subset). Applies via `NodeGraphController::SetZoom`/`SetPanOffset`, which mark the canvas dirty so the next 16ms render tick shows the new view. zoom is clamped to [0.1, 5.0]; pan has no clamp. Coord convention: `screen = zoom * canvas + pan`.
  - `graph_fit_view` — POST `/graph/view/fit` body `{padding?}` (viewport DIPs, default 40). No-op on empty graph.
- **`NodeGraphController::ContentBounds()`** — returns the AABB of all node visuals in canvas (pre-pan/zoom) space. `{0,0,0,0}` when no nodes are laid out.
- **MCP activity indicator on the toolbar.** A single dot next to the MCP toggle pulses amber when the server has handled a request in the last few seconds and turns off when idle. Provides at-a-glance feedback that an external agent is actually connected and active. The amber colour was chosen because the original green was nearly invisible against the toggle's blue Checked background.
- **`Working Space` parameter node + display-profile mirroring.** New ShaderLab Parameter effect (no input pins, no output image pin) that mirrors the active display profile from the top-bar profile selector — live OS-reported caps or any simulated preset / ICC the user has applied — into 14 typed analysis output fields: `ActiveColorMode` (0=SDR, 1=WCG/ACM, 2=HDR), `HdrSupported`, `HdrUserEnabled`, `WcgSupported`, `WcgUserEnabled`, `IsSimulated`, `SdrWhiteNits`, `PeakNits`, `MinNits`, `MaxFullFrameNits`, plus four CIE-xy primaries `RedPrimary` / `GreenPrimary` / `BluePrimary` / `WhitePoint` (each Float2). Bind any downstream property to these fields via the property-binding system — e.g. wire a tone-mapper's peak-nits to `working_space.PeakNits` and it tracks Display Settings or simulated profile changes automatically. Replaces ad-hoc per-effect "follow the working space" toggles. Updated in `MainWindow::UpdateWorkingSpaceNodes()` which runs on `ApplyDisplayProfile`, `RevertToLiveDisplay`, the display-change callback, and once per render tick (cheap node-list walk; only marks dirty when at least one field actually changed, so freshly-added nodes pick up live values immediately without hooking every AddNode site).
- **`DisplayCapabilities` extended with ACM / WCG state** (`activeColorMode`, `hdrSupported`, `hdrUserEnabled`, `wcgSupported`, `wcgUserEnabled`). Sourced from a new `DisplayMonitor::QueryAdvancedColorInfo2()` helper that calls `DisplayConfigGetDeviceInfo` with `DISPLAYCONFIG_DEVICE_INFO_GET_ADVANCED_COLOR_INFO_2` (type 15, requires SDK 10.0.26100). Falls back to deriving `activeColorMode` from `caps.hdrEnabled` when the type-15 query is unavailable. Also trusts DisplayConfig's `bitsPerColorChannel` over the legacy DXGI heuristic, which reports 8 in many WCG configurations even when the actual scanout is 10-bit. All seven preset factories now stamp coherent ACM/WCG flags via the new `StampSimulatedColorMode()` helper so simulated profiles report a self-consistent display mode through the Working Space node.

### Changed
- **The "Regular parameter nodes" branch in `GraphEvaluator::Evaluate` now unpacks the full `PropertyValue` variant** (`bool` → 0/1 float, `int32_t` / `uint32_t` → float, `float2` / `float3` / `float4` → component[0..N]) into `AnalysisFieldValue::components`. Previously only `float` was unpacked, so any vector or boolean property on a parameter node was silently zero. Used by the Working Space node for primary chromaticities (Float2) and capability flags (Float-as-bool); also benefits any future host-managed parameter nodes that need richer types.
- **`Working Space Integration` README section rewritten** to describe the new "bind, don't hide" pattern for tracking the active display profile. Decision log gains entry #51; entry #35 (the `_hidden` suffix convention) cross-references #51 to record that the suffix filter is now legacy-compatibility only.
- **`ICtCp Tone Map (HDR → SDR)` gained a `ToneLift` parameter** (default `0.0` = identity, range `[0..1]`). Adds an anchored polynomial mid-bump on top of the existing I-channel Reinhard compression: `f(x) = x + a·x·(1−x)` evaluated in normalized `[0, peakOut]` I-space then scaled back. Designed to let the operator approximate D2D `HdrToneMap`'s "make HDR readable on SDR" dark-end lift without giving up the hue-preservation property of pure I-channel compression. Quantitatively benchmarked against D2D HDR Tone Map on the `Colors of Journey` HDR test clip: at `ToneLift ≈ 0.6`, dark-region nit counts match D2D within ~10%; at `ToneLift = 0` the effect is its prior pure-compression behavior. Effect bumped from version 9 → 10 (drops `ToneLift` initialized to default on existing graphs). Note: the docstring no longer claims "saturation is preserved by construction" — only hue is. Lifting I without rescaling Ct/Cp can desaturate slightly, especially at higher `ToneLift`.

### Fixed
- **`ICtCpToScRGB` could emit NaN/Inf when `pqLms` exceeded the PQ valid range `[0, 1]`.** The function transformed ICtCp → PQ-encoded LMS via the inverse matrix and then called `PQ_EOTF` on each component without clamping. For modified ICtCp inputs (e.g. tone-mapped I) or out-of-gamut chroma, the matrix product could push an LMS component above 1 (where `PQ_EOTF`'s denominator goes through zero and then negative around `V ≈ 1.16`) or below 0 (where `pow` of a negative is undefined). Added `pqLms = saturate(pqLms);` before the EOTF calls. In-domain values are unaffected; out-of-domain values now saturate to the nearest representable nit value rather than producing NaN that propagates into the inverse XYZ→scRGB matrix. Benefits all 8 ICtCp-using effects.
- **`DispatchSync` was UB on timeout.** The original wait-and-deref pattern closed the event after a 10-second timeout, then dereferenced `*result` without checking `WAIT_OBJECT_0` — and the in-flight lambda still held references to stack `result`/`ex`/`event` which dangled if the caller had returned. Replaced with a `shared_ptr<State>` capture so the lambda can safely complete after the caller times out, an explicit `WAIT_OBJECT_0` check that throws on timeout (caller's `catch` returns 500 cleanly), and a 30s timeout for the heavier compute/readback tools. Closed by the new round-2 routes that need it; old routes benefit too.
- **Snapshot capture no longer suppresses the live editor repaint.** `NodeGraphController::Render()` clears `m_needsRedraw` at the end. `CaptureGraphAsPng()` now snapshots the dirty flag before its render and re-sets it after, so an MCP-driven snapshot taken between frames doesn't cancel the next live render.

## [1.3.9] - 2026-05-05

### Fixed
- **D3D11 compute effects (Channel / Luminance / Chromaticity Statistics) never compiled or dispatched.** `DispatchUserD3D11Compute` started with `if (!node.customEffect->isCompiled()) return;` — but `isCompiled()` checks `compiledBytecode.empty()`, and for D3D11 compute the bytecode is only ever populated *inside* this function via the lazy `runner->CompileShader` path. Chicken-and-egg: every call early-returned, no bytecode was ever stored, the shader never ran, and analysis-output fields stayed empty forever. Removed the early-out for that case so the runner can compile on first dispatch and persist the bytecode back to `def.compiledBytecode` for the cbuffer reflection pass.
- **`D3D11ComputeRunner::CompileShader` discarded the compiled bytecode blob** after creating the `ID3D11ComputeShader` object, leaving `def.compiledBytecode` empty for D3D11 compute effects forever. Cached the blob in `m_bytecode` and exposed it via `GetCompiledBytecode()`; `DispatchUserD3D11Compute` now copies it onto `node.customEffect->compiledBytecode` after a successful compile so the cbuffer-reflection pass that packs user properties has something to reflect against.
- **D3D11 compute cbuffers received raw float bit patterns where shaders declared `uint`/`int`/`bool`.** The Properties panel stores enum-style fields (e.g. `Units`, `ClipSource`) as `float`, but the HLSL declares `cbuffer { uint Units; ... }`. Doing `memcpy(dest, &floatVal, 4)` writes `0x3F800000` (1,065,353,216) into the uint slot, so `if (Units == 1)` was never true and conditional code paths were dead. The pack code now reflects each variable's `D3D_SHADER_VARIABLE_TYPE` and converts via `static_cast<uint32_t>` / `static_cast<int32_t>` based on the declared HLSL type before writing.
- **Analysis-only compute nodes froze their output fields after the first frame.** `needsCompute` was only true on `node->dirty || fields.empty()`, and a Statistics node's own properties don't change frame-to-frame even as the upstream video does. Added a topological dirty-propagation pre-pass at the start of `Evaluate`: any node that's dirty marks all its direct downstream consumers dirty before the eval loop runs. Same pass is also done in `RenderFrame` after `TickAndUploadVideos`, so video-frame updates correctly flow through pixel-shader chains *and* analysis-only compute nodes in the same frame they're decoded. Both passes are idempotent — no-op when nothing is dirty.
- **Effect Designer "Output type" + analysis fields were blank when opening a built-in ShaderLab effect** (or any saved custom effect with typed analysis output). `LoadDefinition` populated inputs / parameters / thread-groups but never restored the `OutputTypeSelector` selection or the analysis-field rows, so opening *Channel Statistics* showed no record of its declared `Min` / `Max` / `Mean` / etc. Refactored the per-row construction in the Add-Field click handler into a reusable `AppendAnalysisFieldRow()` method, then taught `LoadDefinition` to map `def.analysisOutputType` → selector index and rebuild one row per `def.analysisFields` entry with name / type / array length restored.

### Fixed
- **MCP server now accepts `Transfer-Encoding: chunked` requests.** Visual Studio's MCP client uses chunked HTTP rather than `Content-Length`; our raw-Winsock reader was passing the chunk framing (`<hex-size>\r\n<payload>\r\n0\r\n\r\n`) straight to `JsonObject::Parse`, which threw `0x83750007 "Invalid JSON string"` on every connect. The reader now detects chunked encoding, waits for the terminating zero-length chunk, and decodes the framing into the actual JSON payload. Content-Length requests are unchanged. Same path also adds: a non-throwing `JsonObject::TryParse` wrapper that returns a JSON-RPC `-32700 Parse error` response instead of bubbling a `winrt::hresult_error`; correct `202 Accepted` (not `200 OK`) for `notifications/*` per the MCP Streamable HTTP spec; a small `GET /` health-check route so clients that probe before posting don't get a 404; and proper status-text for 202/204/400/500 in the HTTP response builder.
- **All five ICtCp pixel shaders were sampling the same edge texel for every output pixel.** They were calling `Source.Sample(Sampler, uv)` with `uv` from `TEXCOORD`, but D2D `TEXCOORD` is in pixel/scene space, not normalized [0,1]. Every output pixel was reading from texel ~256 with edge clamping, so the entire image came out as one constant color regardless of input. Switched to `Source.Load(int3(uv, 0))` to match the Gamut Highlight / scope pattern that was already correct. Affects: `ICtCp Round-Trip Validator`, `ICtCp Tone Map (HDR → SDR)`, `ICtCp Inverse Tone Map (SDR → HDR)`, `ICtCp Saturation`, `ICtCp Highlight Desaturation`. Effect versions bumped to invalidate cached bytecode.
- **`ReinhardCompressI` / `ReinhardExpandI` were unanchored.** The original form `peakOut * t / (1 + t*(1 - ratio))` had `f(peakIn) = peakOut / (2 - ratio)` instead of `peakOut`, so peaks did not map to peaks: HDR→SDR compression undershot the SDR target, SDR→HDR expansion overshot the HDR target by hundreds of percent (a 1000-nit SDR-white input produced ~14,943 nits at TargetPeakNits=1000). Replaced with the anchored Möbius `f(I) = I·peakIn·peakOut / (peakIn·peakOut + I·(peakIn − peakOut))` and its analytic inverse — same shape near zero (slope 1, "Reinhard" feel in the dark end), but `f(0) = 0`, `f(peakIn) = peakOut` exactly, with a smooth shoulder. Round-trip error stays at FP16 noise (~7e-10 per channel at Gain=100k).
- **`ReinhardExpandI` had its peakIn/peakOut convention inverted in the call site.** The doc-comment said `peakIn = SDR, peakOut = HDR`, but the algebra is the literal inverse of `ReinhardCompressI(peakIn=HDR, peakOut=SDR)`, so the call inside the Inverse Tone Map shader was running the curve in the wrong direction (input got dimmer with higher Strength). Both the doc-comment and the call site now agree: peakIn is the *uncompressed* (HDR) range, peakOut is the *compressed* (SDR) range, for both Compress and Expand.
- **Over-range inputs to the ICtCp tone-mapping helpers walked toward the Möbius asymptote.** A 10,000-nit input through an Inverse Tone Map configured for SourcePeakNits=100 produced 1.4 million nits because the helper extrapolated past its anchor onto the rising branch beyond peakIn. Both `ReinhardCompressI` and `ReinhardExpandI` now clamp their input to the valid input range before mapping, so out-of-domain inputs saturate cleanly to the target peak instead of overshooting.
